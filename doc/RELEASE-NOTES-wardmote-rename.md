# Release notes: Paperclip Pro becomes Wardmote

This release uses only the Wardmote names. Nothing reads the old names any more; an existing install is moved over once, by `wardmote migrate-home`, and the server rewrites the old names in stored agent text on start.

## What changes

- **Command, shim and service.** The CLI command is `wardmote` and a managed install writes only `~/.local/bin/wardmote`. The systemd user unit is `wardmote.service` (`wardmote-<instance>.service` for other instances) and the launchd label is `com.tickernelz.wardmote`. The `paperclip-pro` command, shim, root script and unit name are gone.
- **Home folder.** State lives in `~/.wardmote`. A command that finds an unmigrated `~/.paperclip-pro` stops and asks for `wardmote migrate-home` instead of starting an empty home.
- **Environment.** Only `WARDMOTE_*` names are read. On start the instance `.env` file has its `PAPERCLIP_*` keys renamed in place, with a `0600` backup. Env keys an operator set on an agent keep their names.
- **MCP, headers and skills.** MCP tools are `wardmote*` on the `wardmote` server at `/mcp/wardmote`; old tool names are refused. The public MCP tools and the runner's own tools are `wardmote_*` too (`wardmote_finish`, `wardmote_block`, `wardmote_create_task`, `wardmote_dot_*`, and the rest), and the runner execution prompt moves to revision `wardmote-execution.v7`. Native runs must be drained before the upgrade, because a run that started on the old names cannot finish under the new ones. Headers are `X-Wardmote-*`; `X-Paperclip-*` is refused and redacted in logs. The built-in skills are `wardmote`, `wardmote-board`, `wardmote-converting-plans-to-tasks` and `wardmote-create-agent` under the `tickernelz/wardmote/` key prefix (database migrations 0358 and 0359).
- **Stored agent text.** On every start the server rewrites the retired env, tool, header, route and skill names in agent instruction files, agent settings and their history, routines and chat endpoints. It backs up each changed file and row under `backups/wardmote-rename-<time>/`; a second start changes nothing. `wardmote migrate-names --dry-run` lists the changes without writing.
- **Embedded database.** The embedded PostgreSQL role and database are `wardmote`. On the first start the server renames the old role and database in place through a temporary superuser, which it drops afterwards; it refuses while another process is connected to the old database. Backup files are named `wardmote-*.sql.gz`, and older backups with the retired prefix in the same folder are renamed on the next backup so retention keeps pruning them. Agent run tokens use the `wardmote` issuer and `wardmote-api` audience; tokens minted before the upgrade stop working, so upgrade with no run live.
- **Paperclip Cloud, Labs and EE** are removed: managed-cloud mode, Cloud sign-in, the Cloud connector broker, onboarding seeds and the related routes and UI.
- **Stored modes.** Connections that keep their credentials in the instance vault record `wardmote_vault`, and secrets the instance manages record `wardmote_managed`; database migration 0361 rewrites existing rows and the column defaults. API clients that send or compare the old values must use the new ones.
- **Runner adapter type.** The native runner adapter is `wardmote_runner`, its queued-comment protocol is `wardmote_runner_v1`, comments it authorises record `wardmote_runner_protocol`, and its error codes start with `wardmote_runner_`. Database migration 0362 rewrites agents, their runtime state, task sessions, config history, hire approvals, auth sessions, join requests, cost events and comment metadata. API clients that send or compare the old values must use the new ones.
- **Type and function names.** Exported TypeScript types, classes and functions drop the old name for `Wardmote` (for example `WardmotePluginManifestV1` in the plugin SDK and `useWardmoteIssueRuntime` in the UI). Plugins and integrations that import the old names must rename their imports. The ACPX profiles whose pinned sources changed move to Pi profile 24 and Copilot profile 20; the earlier ones become historical.
- **Stored setting and context keys.** Settings, agent configuration, task sessions, open wake requests and run context use `wardmote*` keys (for example `enableWardmoteDeveloperMode`, `wardmoteMcpToolsets`, `wardmoteWake`). Database migration 0363 renames them in instance settings, agents, their config history, task sessions, open wake requests, plugin settings, and the context of runs from the last 14 days, still queued or running, or carrying secret redactions; older run context keeps its old keys as history. On a copy of production data it took 52 s and touched 7,864 runs, so the first start after the upgrade takes about a minute longer before the server answers. Plugin manifests that still declare the retired minimum-version alias are refused; declare `minimumHostVersion`. The announcement feed keeps its upstream field name.
- **Managed environment marker.** Environments the instance manages carry `managedByWardmote` in their metadata, and the default local environment's description names Wardmote. Database migration 0366 renames the stored key, rewrites the old default description, and rebuilds the index that allows only one managed sandbox.
- **Plugin ids.** The shipped plugins use `wardmote.*` ids (for example `wardmote.plugin-llm-wiki`, `wardmote.workspace-diff` and `wardmote.daytona-sandbox-provider`), so their API routes, issue origins and environment settings use the new ids. Database migration 0365 rewrites installed plugins, their database schema name, applied plugin migrations, managed resources, AI connection pools, plugin issue origins, plugin task sessions, environment plugin settings and lease providers. A plugin whose new id is already installed is left alone. Plugins from other publishers keep their ids.
- **Docker image, Compose and Quadlet.** The image keeps its data in `/wardmote` and its provider pack in `/opt/wardmote-runner/provider-pack`. Compose uses the `wardmote` service, the `wardmote-data` volume and the `docker-wardmote` folder, and its Postgres user, password and database default to `wardmote`. The Quadlet files are `wardmote.pod`, `wardmote.container` and `wardmote-db.container`, with the `wardmote-pgdata` volume, `~/.local/share/wardmote` and `wardmote.env`. When an instance config still names `/paperclip`, the container entrypoint links `/paperclip` to the data directory so stored paths keep working. The smoke and canary scripts read `WARDMOTE_VERSION` and `WARDMOTE_CMD`. Existing Docker installs move their data once; see "Docker installs" below.
- **Public MCP scopes and events.** OAuth scopes are `wardmote:read`, `wardmote:write`, `wardmote:configure` and `wardmote:agent`, and MCP events are `wardmote.task.status_changed`, `wardmote.task.comment_created`, `wardmote.task.document_updated`, `wardmote.dot.work_available` and `wardmote.dot.mailbox_updated`. Database migration 0368 rewrites stored grants, pending authorization and device requests, event subscriptions and queued deliveries, so connected assistants keep working; a client that still requests the old scope names is refused and must reconnect with the new ones. Run trace attributes use the `wardmote.task.run.*` prefix.
- **Stored channel values.** Approvals, grants, autonomy windows and owner relays decided in the board record `wardmote` as their channel, and the local board user's address is `local@wardmote.local`; database migration 0360 rewrites existing rows. API responses carry `wardmote` where they carried the old value.
- **Protocol schema ids.** Runner protocol documents, run results, question sets, receipts and the other versioned payloads carry `wardmote.<name>.vN` schema ids, and JSON Schema `$id`s live under `https://wardmote.dev/schemas/`. Readers accept only the new ids. Database migration 0367 renames the ids that the server and UI read back: the presentation decision in run results and run events (events whose payload is hashed for integrity keep theirs), the agent-files receipt of instruction working copies, the question set of thread interactions, the remote-termination, stop-and-retain and workspace-export-resume records on environment leases, Discord command registrations and Teams personal-recipient deliveries. On start the server also upgrades files written under the old ids: each agent's `file-sync/adopted.json` marker, cached runtime context asset manifests (after re-verifying their files), and native runner state under `runtime/paperclip-runner/durable-sessions`, which is moved to its `quarantine` folder so those warm sessions start fresh; `wardmote migrate-names --dry-run` lists the runner state it would move. Teams file-consent transfers still in flight at the upgrade fail and must be sent again. On a copy of production data it took 44 s and touched 18,607 runs, 18,607 run events, 17,423 working copies and 2 interactions, so the first start after the upgrade takes about a minute longer. Ids bound into pinned or attested runtime artifacts (the ACPX profile declaration and runtime contract, semantic tool receipts, the PRP terminal event, Cursor and Pi distribution and proof records, the closure manifests) stay unchanged until those artifacts are requalified. The Pi and Copilot ACPX profiles whose hashed sources changed move to Pi profile 25 and Copilot profile 21; the earlier ones become historical. Agent instructions, routines and chat endpoint text that mention a renamed id are rewritten on start like the other old names.

## Upgrading an existing install

An install on 2026.1109.x or older still runs the old `update` code, which cannot switch the service over, so the switch takes one extra command:

1. Take a backup while the service runs: `paperclip-pro db:backup`.
2. Stop the service once no agent run is live: `paperclip-pro service stop`.
3. Install the new release without restarting: `paperclip-pro update --version <new> --no-backup`. The service is stopped, so the old code installs the payload and does not restart it.
4. Move everything to the new names: `~/.paperclip-pro/cli/current/node_modules/.bin/wardmote migrate-home` (`--dry-run` prints the plan first). It refuses while a service or embedded database is running. It renames `~/.paperclip-pro` to `~/.wardmote` and leaves `~/.paperclip-pro` as a link so absolute paths stored in the database keep working. It replaces `paperclip-pro.service` with `wardmote.service`, keeping whether it was enabled. It replaces the `paperclip-pro` shim with the `wardmote` shim, and renames the install-store and shell PATH markers.
5. Start it: `wardmote service start`. The server applies the database migrations and rewrites stored agent text.

`npx @tickernelz/wardmote install` and `wardmote update` run step 4 on their own when they find the old layout and the service is stopped.

### Docker installs

Docker, Compose and Quadlet installs keep their data where the old names put it, so move it once before starting the new image. `doc/DOCKER.md` ("Upgrading from the old names") has the commands:

1. Bind mount or quickstart Compose: rename `data/docker-paperclip` to `data/docker-wardmote` and mount it at `/wardmote`.
2. Full-stack Compose: copy the `docker_paperclip-data` volume into `docker_wardmote-data`, and start the stack with `POSTGRES_USER`, `POSTGRES_PASSWORD` and `POSTGRES_DB` set to `paperclip`, because the existing database volume was created with them.
3. Quadlet: stop `paperclip-pod`, remove the old unit files, rename `paperclip.env` and `~/.local/share/paperclip`, copy the `paperclip-pgdata` volume into `wardmote-pgdata`, build `wardmote-local`, copy the new units and start `wardmote-pod`.

The old folders and volumes stay until you remove them.

## Rolling back

`wardmote update --rollback` flips back to the previous payload when it contains the `wardmote` command (2026.1108.0 or newer) and refuses otherwise. An older release does not know the `wardmote.service` name, so restart the service yourself afterwards: `systemctl --user restart wardmote.service`. Database migrations are not reversed, and an older release cannot log in to the renamed embedded database; restore the backup from step 1. Stored agent text can be restored from `backups/wardmote-rename-<time>/`.

## Kept on purpose

- The MIT copyright notice of the upstream project in `LICENSE`.
- Upstream-sync references to `github.com/paperclipai` until upstream sync is decided.
- Applied database migrations, archived plans and earlier release notes, which describe the past.
- The migration code itself, which has to recognise the old names to move them.
